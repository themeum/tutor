# Playwright E2E Suite Review

**Date:** 2026-11-15  
**Scope:** `tests/e2e/` in the free plugin, the Pro suite on `tutor-pro@feat/e2e-coverage` (`24c176636`), the Playwright config, CI workflow, factories, and E2E docs.  
**Criteria:** `playwright-best-practices` skill (structure, locators, assertions/waiting, fixtures, isolation, CI, reporting).

**Verdict:** The suite has a strong foundation — real WordPress, real checkout, isolated test databases, role fixtures, and good failure artifacts. The two biggest problems are **signal quality** (helpers that can silently skip the thing they claim to test) and **CI coverage** (121 of 155 tests, 78%, never run in CI). Locator strategy and suite speed are the next tier.

---

## 1. Executive summary

| Area | Rating | Why |
| --- | --- | --- |
| Structure | B− | Clear `smoke/feature/journey/admin` split, but journey specs are mega-tests (up to 480 s, 621 lines). |
| Locators | C+ | Role and test-id locators exist, but 34% of locator calls are raw CSS; zero `getByLabel`. |
| Waiting | C | 599 web-first assertions is good; 33 `catch(() => …)` calls and 20 `waitForLoadState` calls can hide failures. |
| Isolation | B− | Unique data via factories, but shared seeded rows and global add-on/option state force `workers: 1`. |
| Auth | D | Prototype monkey-patching, self-healing fills, and a nested fallback login path. |
| CI | D+ | Core only; Pro absent; one worker; one Chromium project; WooCommerce path skipped. |
| Coverage | B− | Broad happy paths, but no error/network, visual, accessibility, or console-error checks. |
| Reporting | B | HTML/list, traces, screenshots, video; no JUnit/JSON or shard merge. |

**Top five fixes, in order:**

1. Run the Pro suite in CI (section 6). It is 78% of the test count.
2. Remove silent catches and conditional assertions so a missing UI fails the test.
3. Replace the login hacks with one deterministic login path.
4. Assert exact factory-created data instead of seed rows and `a|b|c` regexes.
5. Enable parallel workers/shards after adding per-test state cleanup.

### Patch status (2026-11-15)

Applied in this pass:

- **P0-2 (core and Pro):** removed conditional `isVisible()` assertions from the admin helpers and specs; assignments and enrollments now require their filter, search, sort, and course-plan controls.
- **P0-3:** login is one deterministic path — no prototype patching, self-healing fills, blur hack, or nested Enter fallback.
- **P0-4:** orders, students, and quiz-attempt tests assert an exact seeded row instead of `student|E2E Student` alternations.
- **P1-3:** the paid-course smoke uses `payWithNativeCheckout` instead of duplicating the checkout flow.
- **P1-5 (partial):** navigation waits no longer swallow timeouts; the settings test clicks the visible toggle instead of force-checking a hidden input.
- **P0-5 (partial):** the settings save now snapshots and restores `payment_settings`, so the seeded manual bank-transfer method survives the admin suite and later checkout tests keep working.
- **P1-8:** JUnit reporter added alongside the list and HTML reporters.
- **P2-1, P2-3, P2-5:** docs versions corrected, Playwright timezone pinned to UTC, and the Pro seeder now honors `E2E_PASSWORD`.

Still open: Pro CI (P0-1), parallel workers (P0-5), async factories (P1-4), `test.step` and the locator overhaul (P1-1/P1-2), error/a11y/visual coverage (P1-7), the Woo profile (P1-6), import style (P1-9), and the remaining Pro `isVisible()` guards in add-ons whose controls are environment-dependent (subscriptions, course bundle, gradebook).

### 2.5 Imports and configuration

- 9 core admin specs and the core journey use the `@e2e/*` alias; smoke and feature specs use relative `../support/*` imports. Both work, but it is inconsistent.
- `playwright.config.ts:44-47` sets `fullyParallel: false`, `workers: 1`, `retries: 0`.

- The Pro project is auto-added when `../../../tutor-pro/tests/e2e` exists (`playwright.config.ts:11-15,30-38`). That is convenient locally and dangerous for CI because “no Pro checkout” silently means “no Pro tests”.

## 3. What is working well

1. **Real end-to-end coverage.** The suite drives a real WordPress install, real database, real admin UI, and the native manual-payment checkout. It is not a mocked UI test suite.
2. **Database isolation is unusually careful.** The `X-WP-Test-Env` header plus host allowlist (`test-config.php`), `WP_TEST_ENV=1` for CLI/cron loopbacks, preflight checks, and separate `local_test`/`local_phpunit` databases are strong safeguards.
3. **Role fixtures.** One storage state per role (`admin`, `instructor`, `student`, `student2`, `manager`, guest) keeps tests readable and avoids repeating login in every spec.
4. **No retries.** Failures are treated as failures. That is the right default for a suite that wants to expose flakiness instead of hiding it.
5. **Failure artifacts.** Trace, screenshot, and video on failure, plus HTML report and server-log upload in CI, make failures diagnosable.
6. **Factories create unique data.** Timestamped course/lesson titles and per-test factories avoid the worst kind of cross-test collisions.
7. **The Pro add-on manifest is a good pattern.** One source of truth for add-on slug, capability, dependencies, probes, and cases; lifecycle tests restore state in `finally`; external integrations are explicitly `fixme` rather than fake-passing.
8. **Server and environment docs.** The walkthrough is detailed and the CI install path is reproducible. The gaps are drift, not missing explanation.

## 4. Findings

### P0-1 — 78% of the suite never runs in CI

**Evidence**

- `tests/e2e/README.md:38`: 155 tests total, 121 Pro.
- `.github/workflows/e2e.yml:42-45` checks out only `themeum/tutor` into `wordpress/wp-content/plugins/tutor`.
- `docs/developer/e2e-test-environment-walkthrough.md:929-931` states CI does not check out Pro, so only core runs.
- `playwright.config.ts:11-15` silently omits the Pro project when the sibling directory is absent.
- The Pro suite exists on `tutor-pro@feat/e2e-coverage` (`24c176636`), but the current Pro checkout is on `feat/videojs-migration` and has no `tests/e2e`.

**Impact**

Pro regressions can merge while core stays green. Pro tests also bit-rot because nobody runs them on a schedule. Local “full suite” and CI “full suite” mean different things.

**Fix**

Add a Pro-owned CI workflow (section 6) or pull Pro into the free workflow with a read-only token. Make the project selection explicit: fail CI when `E2E_PRO=1` and the Pro directory is missing, instead of silently running core only.

### P0-2 — Helpers can pass without exercising the feature

**Evidence**

- `tests/e2e/support/admin.ts:54,67`: `waitForFunction(...).catch(() => {})` swallows a navigation timeout. Most callers assert the URL afterward, so the test usually still fails — but the helper hides the real cause, and a caller that only checks for PHP errors would pass. `clearAdminSearch` (`admin.ts:19-25`) can fall back to a different path and pass even when the clear control is absent.
- `tests/e2e/support/course-builder.ts:58,206,219`: optional UI branches silently skip saving the title, opening settings, or other steps.
- `tutor-pro/tests/e2e/addons/assignments.spec.ts:46,52` and `tutor-pro/tests/e2e/addons/enrollments.spec.ts:49,63,69` wrap the filter and sort assertions in `if (await button.isVisible())`. If the control is missing, the test has no assertion for it.
- 33 `.catch(() => ...)` occurrences across the suite.

**Impact**

False greens and misleading failures. A regression that removes the clear control or an optional builder field can leave the test passing; a broken filter/sort navigation fails later at the URL assertion, pointing at the wrong line. Both erode trust in the run.

**Fix**

- Delete the `.catch(() => {})` on navigation waits. Let the timeout fail with a useful message.
- Assert the precondition before acting: `await expect(filterButton).toBeVisible()`.
- If a control is genuinely optional by design, assert the expected branch explicitly and tag the test so the optional path is visible in the report.
- Use `test.skip` only for environment capability (WooCommerce/Pro/H5P absent), never for “the UI did not appear”.
- Make helpers return the state they observed and assert it at the call site; do not swallow.

### P0-3 — Login is held together with prototype patches and fallbacks

**Evidence**

- `tests/e2e/support/auth.ts:19-43` overrides `HTMLElement.prototype.focus` and `HTMLInputElement.prototype.select` to defeat WordPress’s `wp_attempt_focus()`.
- `auth.ts:74-81` re-fills username/password if the values do not match (“self-heal”).
- `auth.ts:83-118` catches a failed submit, tries Enter, catches again, then extracts an error from three possible selectors.
- `tests/e2e/global-setup.ts` logs in all five roles in one browser; one failure aborts the whole run before any test starts.

**Impact**

The suite changes application behavior to make login work, which can hide a real login regression. The nested fallback makes failures slow and hard to diagnose. A single bad credential or a WordPress login markup change aborts the run in `globalSetup`, before any test and outside the normal per-test report.

**Fix**

- Remove the focus/select monkey-patch. Disable `wp_attempt_focus` in the test environment with a tiny mu-plugin (`remove_action('login_footer', 'wp_attempt_focus')` or the equivalent for the installed WP version), or set the test flag the plugin already uses.
- Use one deterministic path: `fill` → `click` → `expect(page).not.toHaveURL(/wp-login\.php/)`.
- On failure, read `#login_error` once and throw it. Do not retry with Enter or re-fill fields.
- Prefer an API/session bootstrap for storage state if WordPress application passwords are available; keep one UI login test to cover the form itself.
- Move login into a Playwright setup project (`*.setup.ts`) with `dependencies` so setup failures are reported and artifacts are captured. With retries disabled, a setup project is still clearer than `globalSetup`.

### P0-4 — Assertions are too broad and depend on shared seed data

**Evidence**

- `tests/e2e/admin/03-admin-orders-students.spec.ts:11-12`: `toContainText(/student|E2E Student/i)` and `toContainText(/completed|incomplete|unpaid|\$49/i)`. The second matches almost any order state.
- `admin/05-admin-quiz-attempts.spec.ts:19`: same `student|E2E Student` alternation.
- `admin/04-admin-announcements.spec.ts:11,19`: hard-coded `Welcome to Modern JS Bootcamp` from the seeder.
- `journey/01-course-creation-journey.spec.ts` uses the seeded `Web Development` category in six places.
- Pro specs assert seeded strings such as `Modern JavaScript Coding Assignment` and generic `/student/i` rows.

**Impact**

The test can pass while showing the wrong order, the wrong student, or an empty table that happens to contain the word “student”. Seed changes break unrelated tests, and the test does not prove the feature’s data contract.

**Fix**

- Create the record in the test with a unique title and assert that exact title/row/cell.
- For order state, read the factory-created order status and assert it, e.g. `expect(row).toContainText(order.status)`.
- Use `toHaveCount(0)` / `toHaveCount(1)` on the table body for empty-state checks instead of scanning `body` text.
- Replace `a|b|c` regexes with the one expected value; if multiple states are legitimate, assert the set explicitly.
- Keep one seeded-data smoke test if desired, but do not build feature coverage on the seed.

### P0-5 — Global state and `workers: 1` hide isolation problems

**Evidence**

- `playwright.config.ts:44-47`: `fullyParallel: false`, `workers: 1`.
- Pro lifecycle/role/gating tests toggle global add-on state; core journey changes Tutor options (`monetize_by`, course author, enrollment cap).
- Restores are in `finally`, which is good, but a process crash or timeout can leave state behind.
- The seed is global and shared by all specs; `README.md` recommends a full reset when things drift.

**Impact**

The suite cannot shard, runs slowly, and state leaks are only discovered when someone changes test order. A single failure can poison later tests. CI’s 60-minute timeout is a symptom.

**Fix**

- Add fixtures that snapshot and restore add-on/option state per test or per file, not just `finally` inside the test body.
- Split projects: core can run parallel; Pro add-on lifecycle/roles can be serial or use a worker-scoped lock.
- Set `workers` to 2–4 in CI and `fullyParallel: true` for core after the data cleanup; run `--repeat-each=3` to find collisions.
- Shard by file in CI. Each shard gets its own WordPress/MySQL instance, so global DB state is not shared.
- Give every test its own factory-created course/order; reserve the seed for read-only dashboard smoke tests.

### P1-1 — Locator strategy is CSS-heavy and over-narrowed

**Evidence**

- 124 raw `page.locator` calls vs 70 `getByRole` and 50 `getByTestId`; zero `getByLabel`.
- 182 `.first()`, 45 `.last()`, 5 `.nth()`.
- Examples: `checkout.ts:5-7` uses a comma-separated CSS/`:visible` selector; `course-builder.ts:73-75` uses `input[data-input][placeholder="Select date"]:visible`; `smoke/instructor-course.spec.ts:11` uses `.tutor-create-new-course:visible`.
- `admin/01-admin-courses.spec.ts` mixes `.tutor-wp-dashboard-header-title` CSS with role locators.

**Impact**

Selectors break on markup/class changes and `.first()` can silently pick the wrong duplicate. CSS `:visible`/`:has-text` encode state into the selector, so a missing element produces a timeout instead of a clear assertion.

**Fix**

- Prefer `getByRole` for buttons, links, headings, tables, and column headers; `getByLabel` for form fields; `getByTestId` for plugin UI.
- Scope ambiguous locators to a row/container (`row.getByRole('button', { name: 'Edit' })`) instead of `.first()`.
- Add `data-testid` to WordPress-core screens only where a stable role/label is impossible; keep lowercase test IDs as documented.
- Replace `:visible` with an explicit visibility assertion and a scoped locator.
- Add a lint rule or review checklist for new raw CSS selectors.

### P1-2 — Journey specs are mega-tests with no `test.step`

**Evidence**

- Core journey: 571 lines, 6 tests; first test sets a 240 s timeout (`journey/01-course-creation-journey.spec.ts:49,54`).
- Pro journey: 621 lines / 3 tests with a 480 s timeout (`tutor-pro/tests/e2e/journey/01-course-creation-journey.spec.ts:52`), plus 366 lines / 2 tests.
- Zero `test.step` across both suites.
- The first core journey test covers authoring, persistence, frontend rendering, and multiple fields in one block.

**Impact**

A failure in step 12 of 20 gives a trace but no named phase. The test cannot be selectively run or sharded. Long timeouts hide slow paths and make CI feedback slow.

**Fix**

- Split independent scenarios into separate tests: authoring/persistence, visibility, author change, enrollment cap, native checkout, Woo checkout. Keep a serial journey only where the business flow truly requires shared state.
- Add `test.step('author course', ...)`, `test.step('verify frontend', ...)` at minimum; this also improves the custom reporter output.
- Use fixtures for setup (course created, student enrolled) so each test starts at the scenario, not at the login page.
- Reduce per-test timeouts once the steps are isolated; keep a generous timeout only for the true end-to-end journey.

### P1-3 — Checkout flow is duplicated instead of using the helper

**Evidence**

- `tests/e2e/support/checkout.ts:4-81` implements `payWithNativeCheckout`.
- `tests/e2e/smoke/student-paid-course.spec.ts:17-49` reimplements the same buy-now, billing, country update, terms, payment method, and confirmation flow.
- The journey already imports and uses the helper (`journey/01:16,479`).

**Impact**

Two copies drift: a checkout markup change must be fixed twice, and the smoke test can pass with a different flow than the journey.

**Fix**

Use `payWithNativeCheckout(page, email)` in the smoke spec and assert the returned order ID or confirmation. Keep the smoke test as a thin wrapper; keep the detailed assertions in the journey.

### P1-4 — Factories block the event loop and pay WordPress bootstrap per call

**Evidence**

- `tests/e2e/support/factories.ts:28` uses `execFileSync` for every factory call.
- Each call boots WP-CLI, loads WordPress, runs the factory, writes a JSON file, then returns.
- The suite makes many calls per journey test (course, lesson, quiz, enrollment, options, plugins, orders).
- `timeout: 120_000` per call; `maxBuffer: 10 MB`.

**Impact**

Slow tests, no concurrency inside a worker, and a single hung WP-CLI call can consume the test timeout. Shared global state, not this call, is the reason the suite currently needs `workers: 1`; async factories are still required before parallel setup is practical.

**Fix**

- Switch to async `execFile`/`spawn` and `await` it. This alone improves responsiveness and allows parallel setup.
- Batch related creation into one factory call (course + lesson + quiz + enrollment) where the test does not need intermediate state.
- Cache read-only lookups (`getPlugins`, `getCourse`) per worker.
- Consider a small REST/admin-ajax setup API for hot paths; keep WP-CLI for complex seeding.
- Add a factory fixture that records created IDs and cleans them up, instead of accumulating rows.

### P1-5 — Explicit waits and `force: true` remain in hot paths

**Evidence**

- 20 `waitForLoadState('domcontentloaded')` calls, many immediately after a click. If the document is already loaded, this is a no-op; if navigation is pending, it is weaker than `waitForURL` or a web-first assertion.
- 6 `force: true` actions: `admin.ts:48`, `checkout.ts:34`, `smoke/student-paid-course.spec.ts:44`, and Pro toggle clicks.
- One `waitForTimeout(200)` in `content-authoring.ts:253`.
- One `page.waitForFunction(...).catch(() => {})` pair in admin helpers (also P0-2).

**Impact**

`force: true` bypasses actionability checks and can click through overlays or disabled controls. `domcontentloaded` does not prove the UI is ready, so tests either flake or rely on later assertions. The swallowed wait can pass without navigation.

**Fix**

- Replace post-click `waitForLoadState` with the assertion that matters: `expect(page).toHaveURL(...)`, `expect(row).toBeVisible()`, or `waitForResponse`.
- Remove `force: true`; fix the overlay/scroll issue or use `check()` after asserting the input is enabled and visible.
- Replace the 200 ms sleep with an `expect.poll` on the editor state or a response wait.
- Keep `waitForResponse` for AJAX-driven screens; it is already used well in checkout and builder reloads.

### P1-6 — CI runs one profile, one worker, and skips WooCommerce

**Evidence**

- `.github/workflows/e2e.yml` runs only on `pull_request`, one job, `pnpm test:e2e`, `workers: 1` from config.
- `WP_TEST_ACTIVE_PLUGINS: tutor` (`e2e.yml:88`) keeps WooCommerce, Pro, and H5P inactive.
- `journey/01-course-creation-journey.spec.ts:498` skips the WooCommerce test when Woo is inactive, so CI never exercises the Woo checkout path.
- No nightly/scheduled run, no sharding, no `--grep @smoke` fast lane.
- Docs say pnpm 9 / Node 20 (`walkthrough:908`), workflow uses pnpm 12 / Node 24 (`e2e.yml:56,61`).

**Impact**

CI covers the core happy path only, serially. The Woo integration and all Pro add-ons are unguarded. Slow feedback encourages skipping the suite locally.

**Fix**

- Add a fast `@smoke` job on every PR and a full/nightly job with Woo + Pro profiles.
- Matrix/shard the full job (`--shard=1/4`) with a fresh DB per shard.
- Set `WP_TEST_ACTIVE_PLUGINS=tutor,woocommerce` for the Woo profile; `tutor,tutor-pro` (plus dependencies) for Pro.
- Add `--reporter=blob` in shards and `merge-reports` in a final job.
- Fix the docs drift or pin the versions in one place.

### P1-7 — No error-path, visual, accessibility, or console-error coverage

**Evidence**

- 0 `page.route`, 0 `toHaveScreenshot`, 0 console/page-error checks, 0 axe/a11y checks.
- 3 `request.*` calls total, all in Pro add-on helpers.
- The suite covers happy paths and a few permission denials, but not payment failure, API outage, invalid form, or JS error.

**Impact**

Regressions in error handling, layout, and accessibility are invisible. The suite proves “the main flow works,” not “the product behaves correctly when things go wrong.”

**Fix**

- Add a console-error fixture that fails on `pageerror` and `console.error`, with a small allowlist for known WordPress noise. This is cheap and catches real bugs.
- Add error-path tests for checkout failure, invalid coupon, expired enrollment, and add-on dependency gating. Use `page.route` or the existing HTTP stub only for these paths; keep the happy path real.
- Add a handful of stable visual snapshots (course card, checkout summary, builder header), not the whole suite.
- Add axe-core checks on the admin course list, course details, and checkout pages.
- Add `test.step` and `expect.soft` where a page has several independent assertions, so one failure reports all problems.

### P1-8 — Reporting is human-readable but not machine-readable

**Evidence**

- `reporter: [['list'], ['html']]`; custom `progress-reporter.ts` prints steps.
- No JUnit/JSON reporter, no blob/merge for shards.
- Artifacts upload on failure and report always; that part is good.

**Impact**

Hard to track flake rate, slow tests, or historical pass/fail in dashboards. Sharding would produce separate HTML reports with no merge path.

**Fix**

- Add `['junit', { outputFile: 'test-results/junit.xml' }]` and/or `['json', ...]` for CI analytics.
- Use `blob` + `merge-reports` when sharding.
- Keep the custom reporter for local readability; do not make it the only reporter.

### P1-9 — Import style is inconsistent

**Evidence**

- Admin specs and the journey use `@e2e/support/*`.
- Smoke and feature specs use `../support/*`.
- Pro specs use `@e2e/support/*` plus `../support/test` for the local re-export.

**Impact**

Minor, but it makes refactors and lint rules harder. A move of `support/` breaks one group and not the other.

**Fix**

Standardize on `@e2e/*` for cross-directory imports and relative imports only for same-directory files. Add an ESLint `no-restricted-imports` rule or a review checklist.

### P2 findings

1. **Docs drift.** `docs/developer/e2e-test-environment-walkthrough.md:908` says pnpm 9 / Node 20; `.github/workflows/e2e.yml:56,61` uses pnpm 12 / Node 24. The README’s 155-test count assumes a Pro checkout; without it, `pnpm test:e2e` runs 34 tests. State the condition next to the number.
2. **Pro `fixme` cases need owners/dates.** Five `test.fixme` placeholders (external integrations, Google Classroom, social login, multi-instructors, auth verification) are honest, but the README’s quarantine policy asks for an owner, failing-run link, and a two-week fix/delete deadline. These are manual coverage, not quarantined flakes; label them as such.
3. **Time-dependent tests.** Enrollment validity, content drip, and certificate dates use real dates. Set `TZ=UTC` in config/CI and use a clock fixture or factory-relative dates so a run near midnight/timezone boundaries does not flake.
4. **Local server prerequisite is manual.** `README.md:17` requires an already-running local site; CI starts `wp server` itself. This is documented, not a bug, but it is the main onboarding friction. If auto-start returns, keep `PHP_CLI_SERVER_WORKERS` opt-in locally because of the macOS forked-worker crashes noted in the project history.
5. **Pro seeder password caveat.** `docs/developer/e2e-test-environment-walkthrough.md:1053-1056` notes that `tutor-pro/bin/e2e/seed-pro.php` resets the instructor password to literal `password`, breaking a custom `E2E_PASSWORD`. Fix the Pro seeder to read `E2E_PASSWORD`; otherwise Pro CI must use the default password.
6. **Support files mix concerns.** `content-authoring.ts` (397 lines), `factories.ts` (392), and `course-builder.ts` (318) combine selectors, actions, assertions, and setup. Split by page/feature when touching them; do not rewrite just for size.

**Do not:** add retries, mock the core happy path, vendor Pro tests into the free repo, or replace E2E with API tests. The suite’s value is that it drives the real product; fix the signal and the CI coverage instead.

### 5.1 Architecture decisions

**Page objects or fixtures?** Use all three, as the suite already does: fixtures for lifecycle, helpers for stateless flows, page objects only where a screen has state and many interactions.

- Keep `support/test.ts` role fixtures as the auth/context boundary. They are the one thing every test needs and they own teardown.
- Keep `checkout.ts`, `admin.ts`, and `builder.ts` as helpers. Each is one linear flow; a class would add ceremony without shared state.
- `course-builder.ts` is the only real POM candidate: 316 lines, a multi-step wizard, and repeated `stamp`/title/course-id plumbing across the journey specs. If a third spec starts using the builder, convert it to a `CourseBuilder` class exposed as a fixture that owns the course id and title. Do not rewrite it just for size.
- Do not build page objects for one-off admin screens. A POM pays off when the same screen is driven from several specs and has non-trivial state; most admin specs here touch a screen once.

**Multiple workers?** Not yet, and `workers: 1` is the symptom, not the cause. The suite shares one database and mutates global options and add-on state. Today’s run proved it: the admin settings save regenerated `payment_settings`, dropped the seeded bank-transfer method, and broke a later checkout test. More workers would multiply that class of failure.

Sequence:
1. Make state restorable per test (snapshot/restore options, add-on config, and `payment_settings` in a fixture, not only in a test’s `finally`).
2. Make factories produce unique data so specs do not depend on the shared seed.
3. Split core into read-only specs (parallel-safe) and mutating specs, then try `workers: 2` plus `--repeat-each=3` locally.
4. In CI, shard by file with a separate WordPress/MySQL instance per shard. Keep Pro serial until add-on state is fixture-scoped; sharding is the only parallelism that survives global DB state.

**Factories through Tutor AJAX/REST?** No. Seed through WP-CLI/PHP factories, not through the product’s own endpoints:

- The AJAX/REST endpoints are part of what the suite verifies. Seeding through them means a broken endpoint still produces a green test, and setup inherits nonce, auth, and UI-contract coupling.
- The current factories already write directly with `wp_insert_post`/`update_option`, which is the right boundary. The cost is `execFileSync` booting WordPress per call, not the transport.
- Fix the cost by batching: one async `execFile` call per test (or one PHP process that reads a JSON-lines payload), instead of one synchronous boot per factory call. That keeps setup independent of product code and removes the event-loop block.
- Use direct PHP for anything the UI cannot do (order completion, payment state), which is already how `tutor_order_complete` and `wc_order_complete` work.
- If batching is not enough, a `WP_TEST_ENV`-gated batch seeder endpoint is acceptable, but it is a new product surface to secure and maintain; exhaust the WP-CLI batch first.

## 6. Running the private Pro tests in CI

Yes, this is solvable without copying Pro tests into the free repo. The Pro tests already live in `tutor-pro/tests/e2e` and import shared helpers from the free plugin via `@e2e/*`. The free config auto-detects the sibling directory. The only question is which repository owns the workflow and how it gets read access to the other repo.

### Option A — Pro-owned workflow (recommended)

Run the workflow in `tutor-pro` on Pro PRs, pushes, and a nightly schedule. It checks out both plugins into the layout the config expects:

```text
wordpress/wp-content/plugins/tutor       # free, public
wordpress/wp-content/plugins/tutor-pro   # private, this repo
```

The Pro repo’s default `GITHUB_TOKEN` can read itself. The free repo is public, so no cross-repo secret is needed. This keeps Pro code and any Pro-specific secrets in the private repo and gates Pro PRs where the tests live.

Sketch:

```yaml
name: E2E (Pro)

on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: '0 3 * * *'

jobs:
  e2e:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: wordpress
        ports: ['3306:3306']
        options: >-
          --health-cmd="mysqladmin ping -h 127.0.0.1 -proot"
          --health-interval=10s --health-timeout=5s --health-retries=12
    env:
      WP_ROOT: ${{ github.workspace }}/wordpress
      PLUGIN_DIR: ${{ github.workspace }}/wordpress/wp-content/plugins/tutor
      PRO_DIR: ${{ github.workspace }}/wordpress/wp-content/plugins/tutor-pro
      WP_TEST_DB_NAME: wordpress_test
      WP_PHPUNIT_DB_NAME: wordpress_phpunit
      WP_TEST_DB_USER: root
      WP_TEST_DB_PASS: root
      WP_TEST_DB_HOST: 127.0.0.1
      SITE_URL: http://localhost:8888
      E2E_BASE_URL: http://localhost:8888
      E2E_PRO: '1'
      WP_TEST_ENV: '1'
    steps:
      - uses: actions/checkout@v4
        with:
          path: wordpress/wp-content/plugins/tutor-pro
      - uses: actions/checkout@v4
        with:
          repository: themeum/tutor
          path: wordpress/wp-content/plugins/tutor
      # PHP, WP-CLI, pnpm, Node, MySQL setup as in the free workflow
      - run: |
          pnpm --dir "$PLUGIN_DIR" install
          pnpm --dir "$PLUGIN_DIR" build-dev
          pnpm --dir "$PRO_DIR" install
          pnpm --dir "$PRO_DIR" build-dev
      - run: |
          php "$PLUGIN_DIR/tests/support/install.php" --yes
          php "$PLUGIN_DIR/tests/support/preflight.php"
        env:
          WP_TEST_ACTIVE_PLUGINS: tutor,tutor-pro
      - run: |
          WP_TEST_ENV=1 wp server --host=localhost --port=8888 --path="$WP_ROOT" &
          # wait for HTTP 200, then:
          pnpm --dir "$PLUGIN_DIR" test:e2e
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: wordpress/wp-content/plugins/tutor/tests/e2e/report/
```

**Why `localhost` and not `127.0.0.1`:** the Pro license gate bypasses `localhost`/`.local`. The free CI uses `127.0.0.1`; Pro CI must use `localhost` (or add `127.0.0.1` to the test bypass in Pro).

**Why `WP_TEST_ACTIVE_PLUGINS: tutor,tutor-pro`:** the free CI sets `tutor` only, which keeps Pro inactive. Pro tests will fail with “add-on disabled” if Pro is not active. Omit the variable to let the installer auto-activate every plugin present, or list the exact profile.

**Why both builds:** the free suite needs free assets; Pro add-ons need Pro assets. The walkthrough already says to build Pro first for local runs.

### Option B — Free workflow pulls Pro with a read-only token

Use this only if free PRs must be gated by Pro tests. Add a secret to `themeum/tutor` (fine-grained PAT with `Contents: Read` on `tutor-pro`, or a GitHub App installation token), then:

```yaml
- uses: actions/checkout@v4
  with:
    repository: themeum/tutor-pro
    token: ${{ secrets.TUTOR_PRO_TOKEN }}
    path: wordpress/wp-content/plugins/tutor-pro
```

Guard fork PRs: `pull_request` from a fork does not receive secrets. Run this job only for internal PRs (`if: github.event.pull_request.head.repo.full_name == github.repository`) or on `push`/nightly. Never use `pull_request_target` with a checkout of untrusted PR code.

### Option C — `repository_dispatch` from free to Pro

The free workflow sends a dispatch to `tutor-pro` after its own E2E job; the Pro workflow checks out the free repo at the dispatched SHA and runs both suites. This keeps Pro secrets in Pro but still needs a token in the free repo to send the dispatch. It is a good fit if you want Pro tests to run after free CI without giving free CI direct read access to Pro code.

### What not to do

- Do not copy `tutor-pro/tests/e2e` into the free repo; it breaks the ownership boundary and leaks private tests.
- Do not make the Pro project silently optional in CI. If `E2E_PRO=1` and the directory is missing, fail with a clear message.
- Do not run the full 121-test Pro suite serially on every PR if it exceeds the budget. Shard it (each shard gets its own MySQL service) or run the full set nightly and a `@p0` subset on PRs.

### Practical checklist for the Pro job

- [ ] Sibling layout: `plugins/tutor` and `plugins/tutor-pro`.
- [ ] Free + Pro dependencies installed and assets built.
- [ ] `WP_TEST_ACTIVE_PLUGINS` includes `tutor-pro` (and any add-on dependencies such as WooCommerce).
- [ ] `SITE_URL`/`E2E_BASE_URL` use `localhost` so the Pro license gate is bypassed.
- [ ] `WP_TEST_ENV=1` on the web server so cron loopbacks use the test DB.
- [ ] `E2E_PRO=1` and a hard failure if the Pro directory is absent.
- [ ] Pro seeder reads `E2E_PASSWORD` (fix the literal-password caveat first).
- [ ] Artifacts: HTML report always; traces/screenshots/video and server log on failure.
- [ ] Nightly full run, PR `@p0` run, and a concurrency group per PR.
